# 易腐品动态折扣强化学习：源码技术说明

## 1. 文档用途

本文档用于快速理解 `src/` 中的代码结构、数据流和实验顺序。它以当前本地源码为准，重点说明每个模块为什么存在、读取什么、执行什么以及生成什么。

项目研究的问题是：在生鲜零售销量受到缺货截断（stockout censoring）的情况下，使用恢复后的需求信号训练动态折扣策略，能否提高易腐库存的经济价值并控制浪费。

最终 held-out test 保留了负结果：在锁定的 60 个 HIGH_RISK_B episodes 上，没有 learned policy 超过 `always_0pct`。因此，本项目的贡献不是证明 RL 必然优于零折扣，而是建立并审计了从需求恢复、半合成环境、策略训练到锁定测试的完整决策实验流程。

---

## 2. 整体实验流程

```text
FreshRetailNet 原始数据
        ↓
数据标准化、完整时间序列抽样、chronological split
        ↓
Stockout-aware demand recovery
        ↓
Observed / recovered markdown-response calibration
        ↓
Shelf life、库存年龄与成本情景
        ↓
41 维 state、6 个 action 的 Gymnasium pricing environment
        ↓
Environment mechanical validation
        ↓
Original PPO → Scenario-Balanced PPO → DQN robustness comparison
        ↓
固定 validation manifest 上的 checkpoint selection
        ↓
候选、协议和文件 hash 锁定
        ↓
一次性 held-out test 与 13-policy baseline ladder
        ↓
最终表格、图形和结论
```

### 2.1 三类信息必须区分

| 类型 | 项目中的例子 | 解释边界 |
|---|---|---|
| 真实观测 | store、SKU、日期、销量、库存、促销和天气 | 来自 FreshRetailNet，经标准化和时间切分后使用 |
| 模型估计 | recovered demand、不同 markdown 下的预测需求 | 是统计代理或 model-implied response，不是真实 latent demand 或因果弹性 |
| 情景假设 | shelf life、库存年龄、采购成本、处置成本和 physical waste | 用于构建受控环境，不能直接解释为某零售商的真实经营参数 |

---

## 3. 最重要的运行口径

- **State（状态）**：固定 41 维，分为 inventory、perishability、demand、time/history 和 context 五组。
- **Action（动作）**：`{0: 0%, 1: 5%, 2: 10%, 3: 20%, 4: 30%, 5: 40%}` markdown。
- **库存流转**：使用 FEFO，先销售最临期库存；未售出的最临期 bucket 成为 physical waste，其余库存老化一天。
- **Demand（需求）**：由 observed 或 recovered response model 根据当前 state 和 action 预测；主环境使用 deterministic demand。
- **Reward（奖励）**：主实验使用 normalized financial reward；reward 不通过 `VecNormalize` 再标准化。
- **主评价指标**：normalized accounting profit，而不是训练 loss 或单独的累计 reward 图。
- **数据隔离**：train 用于拟合，validation 用于 checkpoint/model selection，held-out test 仅在候选与协议锁定后使用。

## 5. 各 Python 模块说明

## 5.1 `freshretail_data_processing.py`：数据准备

**为什么需要**

原始 FreshRetailNet 数据规模较大，字段和文件格式需要先审计。RL episode 依赖完整时间轨迹，因此不能随机抽取独立行。

**主要操作**

- `discover_files()` 和 `inspect_schemas()` 扫描文件并抽样检查 schema。
- `detect_column_candidates()` 根据列名、类型和样例值识别时间、store、SKU、销量、库存和折扣字段。
- `standardize_columns()` 将确认后的字段转换为项目统一列名。
- `analyze_timeseries()`、`analyze_stockouts()` 和 `analyze_promotions()` 检查时间间隔、缺货与促销覆盖。
- `select_modeling_subset()` 以完整 store-product series 为单位抽取代表性子集。
- `trim_to_continuous_window()` 保留连续时间窗口。
- `add_time_split()` 按时间顺序生成 train、validation 和 test。

**输入与输出**

- 输入：本地 FreshRetailNet train/eval 文件。
- 输出：`freshretail_modeling_subset.parquet`、字段映射、split summary、代表性审计表和诊断图。

**与研究问题的关系**

该模块建立后续需求恢复和 RL 环境共同使用的数据基础，并在最前端控制 temporal leakage。

## 5.2 `latent_demand_recovery.py`：缺货需求恢复

**为什么需要**

缺货时 `observed sales = min(true demand, available inventory)`，因此观察销量只是潜在需求的下界，不能直接视为完整需求。

**主要操作**

- `create_censoring_labels()` 区分 possible-stockout、ambiguous 和 likely-uncensored records。
- `engineer_features()` 构造日历、库存、促销、lag 和 rolling features；历史特征只使用当前时点之前的数据。
- `train_models()` 在 likely-uncensored training rows 上拟合历史均值、梯度提升和 ExtraTrees 候选。
- `artificial_censoring_validation()` 对原本可观察的销量人为截断，再比较恢复值与原销量。
- `select_recovery_model()` 只根据 validation 指标选模型。
- `recover_demand()` 仅向上修正 possible-stockout rows，其他记录保留 observed sales。

**输入与输出**

- 输入：预处理后的 modeling subset。
- 输出：recovered-demand parquet、模型 bundle、人工截断验证表和恢复诊断图。

**与研究问题的关系**

它生成 recovered-demand proxy，使项目可以比较 observed-calibration 与 recovered-calibration 两条决策管线。该比较不是 ExtraTrees 单一步骤的孤立因果效应，因为 demand history 和 response model 也随 calibration mode 改变。

## 5.3 `discount_response.py`：折扣响应校准

**为什么需要**

历史数据只记录实际执行的折扣，但环境必须估计同一 state 下其他 action 可能产生的需求。

**主要操作**

- `audit_markdown_support()` 统计各 markdown level 的样本支持度。
- `confounding_audit()` 检查折扣与门店、商品、库存风险、促销和需求水平的共变。
- `engineer_features()` 构造时间、编码、需求历史、库存、缺货和 markdown interaction features。
- `fit_response_models()` 分别拟合 observed-demand 与 recovered-demand response model。
- `response_curves()` 固定其他 state features，逐档修改 markdown 并预测需求。
- `support_for_levels()` 标记 weak-support 和 extrapolation risk。

**输入与输出**

- 输入：包含 observed sales 与 recovered demand 的数据。
- 输出：两套 response model、support/confounding audit、response curves 和 action ranking。

**与研究问题的关系**

该模块为环境提供 `demand(state, markdown)`。输出只能解释为 observational/model-implied response，不能称为因果价格弹性。

## 5.4 `perishability_scenarios.py`：易腐库存情景

**为什么需要**

FreshRetailNet 没有完整的 batch shelf life、库存年龄、实际浪费和成本字段，而这些变量是易腐品 markdown 决策所必需的。

**主要操作**

- `variable_source_registry()` 标记变量来自 observed、model-estimated 或 scenario-assumed。
- `shelf_life_scenarios()` 定义不同保质期情景。
- `inventory_initialization_scenarios()` 定义库存覆盖和年龄结构。
- `economic_scenarios()` 定义采购成本与处置成本比例。
- `scenario_grids()` 组合核心场景。
- `simulate_policy()` 在进入 Gymnasium 环境前运行固定策略 sanity checks。

**输入与输出**

- 输入：recovered demand、response artifacts 和商品/库存特征。
- 输出：perishability master config、scenario grid、变量来源表与 FEFO 检查。

**与研究问题的关系**

它把真实需求背景与透明的库存假设连接起来，形成 semi-synthetic controlled experiment。

## 5.5 `pricing_env_operational.py`：核心定价环境

**为什么需要**

这是 PPO 和 DQN 共用的 Gymnasium environment，负责把需求、价格、库存年龄、浪费和利润组成序贯决策问题。

**主要操作**

- `OperationalPerishablePricingEnv.__init__()` 加载 processed data、scenario config 和两套 response model，定义 `Discrete(6)` action space 与 41 维 observation space。
- `reset()` 在指定 split 中选择完整 episode，初始化库存 bucket、需求历史和 accounting state。
- `_get_obs()` 按锁定顺序构造 41 维 observation。
- `_predict_demand()` 根据 calibration mode 和当前 markdown 生成 model-implied demand。
- `_issue_fefo()` 从最临期 bucket 开始扣减销量。
- `step()` 依次完成 action 映射、需求预测、销售约束、FEFO、到期、aging、利润与 reward 更新。
- `_info()` 输出 revenue、profit、waste、sell-through、stockout 和守恒检查。

**单步数据流**

```text
action index → markdown → selling price → predicted demand
→ sales=min(demand, inventory) → FEFO issue → expiry/aging
→ accounting → normalized reward → next state
```

**输入与输出**

- 输入：recovered dataset、scenario config、observed/recovered response models。
- 输出：每一步的 observation、reward、terminated/truncated 和 accounting diagnostics。

**与研究问题的关系**

所有 learned 和 baseline policies 在相同环境机制下比较，因此策略差异不会来自不同库存或 accounting 实现。

## 5.6 `validate_pricing_env_operational.py`：环境验证

**为什么需要**

训练曲线正常并不能证明 simulator 正确。库存丢失、采购成本重复扣除或 action 无效都会产生误导结果。

**主要操作**

- `run_api_checks()` 检查 Gymnasium 与 SB3 接口。
- `accounting_validation()` 检查负库存、库存守恒、利润恒等式与非有限数值。
- `action_effect_audit()` 从同一 state 分别执行六个 action，确认价格和需求响应发生变化。
- `split_boundary_violations()` 检查 episode 是否跨越数据 split。
- `calibration_transmission()` 比较 observed/recovered signal 是否传递到决策结果。

**输入与输出**

- 输入：已构建的 pricing environment 和 artifacts。
- 输出：API、accounting、action-effect、reward-scale 和 sensitivity tables。

## 5.7 `train_ppo_operational.py`：Original PPO

**为什么需要**

使用同一 PPO 实现分别训练 observed-calibration 和 recovered-calibration agent，检验需求表示变化是否传递到策略行为和价值。

**主要操作**

- `make_agent_specs()` 创建 observed/recovered agent specifications。
- `make_vec_env()` 连接多个环境，并使用 `VecNormalize(norm_obs=True, norm_reward=False)`。
- `ppo_params()` 和 `policy_kwargs()` 定义 Stable-Baselines3 PPO 参数与网络。
- `TrainingMetricsCallback` 定期保存 checkpoint、VecNormalize 和训练指标。
- `train_one_agent()` 执行 `model.learn()`。
- `evaluate_model()` 在 validation episodes 上记录 profit、waste 和 action behavior。

**输入与输出**

- 输入：OperationalPerishablePricingEnv、PPO config 和训练 split。
- 输出：PPO checkpoints、normalization state、training/validation tables 和行为诊断。

**与研究问题的关系**

Original Observed PPO 与 Original Recovered PPO 比较的是两条 calibration pipelines，而不是宣称 PPO 本身是算法创新。

## 5.8 `evaluate_ppo_operational.py`：PPO validation 评估

**为什么需要**

训练结束时的 final checkpoint 可能发生 action collapse，因此不能仅凭最后一步或 aggregate return 选择模型。

**主要操作**

- 创建或读取固定 validation episode manifest。
- 加载 PPO checkpoint 及匹配的 VecNormalize。
- 在相同 episodes 上运行 PPO、固定策略和规则策略。
- 生成 paired comparison、action distribution、entropy 和 state-dependence diagnostics。

**边界**

该模块不调用 `model.learn()`，也不是最终 held-out test。

## 5.9 `train_ppo_recovered_redesign.py`：Scenario-Balanced PPO

**为什么需要**

原始训练分布中，真正需要正折扣的高库存、临期和低 sell-through 状态较少，可能导致策略趋向单一动作。

**主要操作**

- `load_meaningful_scenarios()` 读取既有 validated training scenarios。
- `scenario_sampling_weights()` 提高高库存、短 shelf life 和存在浪费场景的训练曝光。
- `ScenarioBalancedEnv` 只改变 episode/scenario sampling，不改变 core environment。
- `train_variant()` 训练 BALANCED 和 BALANCED_STABLE 两个预设变体。
- `evaluate_checkpoint()` 在未改变的 validation manifest 上检查 profit、decision error、action share 和 entropy。
- `compare_and_select()` 使用多指标规则选择 checkpoint。

**最终模型口径**

最终记录的 selected Balanced PPO 是 `BALANCED__checkpoint_20000`，不应描述成采用 BALANCED_STABLE 超参数的模型。

**与研究问题的关系**

这是 training-exposure redesign，不是新的 PPO 算法，也没有改变 reward、action space 或 validation distribution。

## 5.10 `high_risk_b_planning_distillation.py`：补充 planning 诊断

**为什么需要**

在总体环境中正折扣机会较少，因此该模块聚焦 HIGH_RISK_B 状态，检查有限视野动态决策是否存在可学习信号。

**主要操作**

- `is_high_risk_b()` 使用锁定阈值识别高库存、临期和低预计 sell-through 状态。
- `simulate_sequence()` 对有限 action sequence 复制环境并累计 reward。
- `planning_action_and_margin()` 比较不同 first action 的有限视野价值。
- `build_training_labels()` 只在 train episodes 上生成 planning labels。
- `grouped_training_eval()` 和 `validate_distilled_model()` 训练并验证轻量蒸馏策略。

**边界**

这是补充实验，不是最终主模型；horizon-3 planning 也不是全局 optimal oracle。相关差值应称为 diagnostic oracle value gap，而不是真实 regret。

## 5.11 `train_dqn_high_risk_b.py`：DQN 训练

**为什么需要**

DQN 提供 value-based robustness comparison，用于检查 PPO 的结果是否强烈依赖 policy-gradient 算法形式。

**主要操作**

- `HighRiskBTrainingEnv` 从锁定的 HIGH_RISK_B train population 选择 episode。
- `make_vec_env()` 使用与 PPO 相同的 core environment 和 observation normalization。
- `DQNCheckpointCallback` 定期保存模型、VecNormalize 和训练状态。
- `evaluate_checkpoints()` 在固定 validation manifest 上逐 checkpoint 评估。
- `seed_stability()` 比较多个 seed 的方向与稳定性。
- `select_candidate()` 根据预设 validation 规则选择候选。

**输入与输出**

- 输入：HIGH_RISK_B train episodes、固定 validation manifest 和 pricing environment。
- 输出：DQN checkpoints、normalization files、paired validation tables 和候选记录。

**边界**

该模块不读取 held-out test。

## 5.12 `dqn_statistical_audit_and_ensemble.py`：多 seed 审计与 ensemble

**为什么需要**

单个 seed 可能偶然表现较好，逐行 pooled inference 也会夸大独立样本数。

**主要操作**

- `clustered_inference()` 先在 episode 内聚合，再以 episode/scenario cluster 为统计单位。
- `load_members()` 加载三个已选 DQN checkpoints 及各自 VecNormalize。
- `q_values()` 用每个成员自己的 normalization 计算六个 action 的 Q-values。
- `ensemble_action()` 等权平均三个成员的 Q-values，再选择 argmax action。
- `evaluate_ensemble()` 在固定 validation manifest 上评估 ensemble。

**边界**

这是 validation 阶段的模型锁定步骤，不训练模型、不读取 test split。

## 5.13 `final_dqn_ensemble_test_evaluation.py`：锁定 held-out test

**为什么需要**

开发阶段的所有调参和模型选择必须在 validation 上完成，最终 generalization evidence 需要独立的一次性 test protocol。

**主要操作**

- `write_candidate_lock()` 在读取 test split 前记录 ensemble members、baseline、action mapping 和 artifact hashes。
- `write_protocol()` 锁定 endpoint、bootstrap 和状态判定规则。
- `build_test_manifest()` 按锁定 HIGH_RISK_B 定义创建 60-episode test manifest。
- `evaluate_policy_episode()` 在相同 episode 上运行 DQN ensemble 与 `always_0pct`。
- `bootstrap_summary()` 以完整 episode 为独立单位对 paired difference 重采样。
- `summarize_test()` 汇总 profit、CI、win/tie/loss、waste、sell-through 和 action behavior。

**一致性修正说明**

运行时 action index 始终由环境的 `ACTION_MARKDOWNS` 转换为 `0/5/10/20/30/40%`。历史 lock JSON 中曾保留旧 action-mapping metadata，但没有参与训练或 test rollout。当前代码已从环境常量生成未来 lock metadata，并把可选诊断字段完整性与 primary numerical validity 分开检查。

**最终结果口径**

锁定 DQN ensemble 未超过 `always_0pct`；该结论不因上述 reporting/metadata 修正而改变。

## 5.14 `final_test_baseline_ladder.py`：最终策略阶梯比较

**为什么需要**

只比较一个 learned policy 和一个 baseline 无法说明策略在完整决策集合中的位置。

**主要操作**

- 加载锁定的 PPO、Balanced PPO、DQN ensemble 和同一 60-episode test manifest。
- `fixed_or_rule_action()` 实现固定折扣和两个预先定义的风险规则。
- `evaluate_episode()` 在相同环境口径下记录 profit、waste、sell-through 与 action sequence。
- `paired_diff()` 计算对 `always_0pct`、random 和固定折扣策略的 episode-level differences。
- `pareto_frontier()` 识别 profit-waste frontier。

**边界**

这是 post-hoc descriptive baseline ladder。它不能替代最初锁定的 primary comparison，也不能选择性遗漏优于 learned policy 的 baseline。

## 5.15 `final_report_figures.py`：报告图形

**为什么需要**

将多个阶段的锁定表格转换为风格统一、可追溯的报告图形。

**主要操作**

- 读取已有 PPO/DQN、planning 和 sustainability tables。
- 绘制 validation curve、action distribution、entropy、policy comparison 与 profit-waste trade-off。
- 生成 figure inventory 和解释文档。

**边界**

该模块不训练模型，也不重新执行 environment rollout。

## 7. 训练、评估与报告的区别

| 类别 | 模块 | 是否训练模型 | 是否应在查看已有结果时运行 |
|---|---|---:|---:|
| 数据准备 | `freshretail_data_processing.py` | 否 | 否，除非重建 processed data |
| 需求与响应建模 | `latent_demand_recovery.py`、`discount_response.py` | 是，监督模型 | 否，除非重建 calibration artifacts |
| 环境与验证 | `pricing_env_operational.py`、`validate_pricing_env_operational.py` | 否 | 环境验证可运行，但不是查看结果所必需 |
| PPO 训练 | `train_ppo_operational.py`、`train_ppo_recovered_redesign.py` | 是 | 否，计算较重 |
| DQN 训练 | `train_dqn_high_risk_b.py` | 是 | 否，计算较重 |
| Validation/锁定 | `evaluate_ppo_operational.py`、`dqn_statistical_audit_and_ensemble.py` | 否 | 通常不需要重跑 |
| Held-out evaluation | `final_dqn_ensemble_test_evaluation.py`、`final_test_baseline_ladder.py` | 否 | 不应为了浏览仓库而重跑 |
| 报告生成 | `final_report_figures.py` | 否 | 只在需要从既有表格重建图时运行 |

## 8. 最终结果与解释边界

锁定 held-out test 的核心结果保持不变：

- `always_0pct` mean normalized profit：`0.447999`
- Scenario-Balanced Recovered PPO：`0.435909`
- Locked DQN ensemble：`0.425721`
- DQN 相对 `always_0pct` 的 paired mean gain：`-0.022278`
- 95% bootstrap CI：`[-0.027486, -0.017319]`
- 60 个 paired held-out episodes，13 个最终比较 policies
- 没有 learned policy 超过 `always_0pct`

可辩护的结论是：stockout-aware demand recovery、scenario-balanced exposure 和 value-based DQN 改变了部分策略行为，但在当前 semi-synthetic assumptions 与锁定 HIGH_RISK_B held-out population 下，这些 learned policies 没有产生超过强零折扣基线的经济价值。

该结论不应扩展为“RL 对所有易腐品定价都无效”。Recovered demand 仍是 proxy，markdown response 不是 causal elasticity，shelf life、库存年龄、成本与 physical waste 含有情景假设；环境支持受控比较，不支持直接部署声明。
